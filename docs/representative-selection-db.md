# 代表意見の選び方：DB担当への相談

設問カードに出す「代表意見（賛成・反対 各3件）」を、次の2つの軸で選ぶ仕組みを作っています。
アプリ側の選び方（`app/src/app/lib/representatives/`）はできていて、DBまわりの判断が必要なところで止めていました。
以下のとおり決まり、DB への適用まで終わっています（最後の「決まったこと」を参照）。

## 選び方の概要

1. **なるほど**：賛成側・反対側の両方から「なるほど」をもらっている意見を高くする
   - 点数 = `合計 ＋ 少ないほうの側の数`（片方の側から5件より、両方から2件ずつのほうが高い）
   - 押した人の投票が 4〜5 なら賛成側、1〜2 なら反対側。3 や未投票のなるほどは数えない
2. **観点**：選んだ意見どうしの内容が重ならないようにする
   - 意見の文章を Gemini の埋め込み（`gemini-embedding-001`、768次元）でベクトルにし、似ている意見を避ける（MMR）
   - 類似度 0.9 以上は同じ観点とみなし、ほかに候補があるうちは選ばない
3. なるほどがなければ新しい順。ベクトルがなければなるほどだけで選ぶ

## 相談したいこと

### 1. 賛成側・反対側に分けた「なるほど」の数を読む方法

- 数える関数 `private.get_thread_reaction_counts(target_frame_id)` はすでにあり、`service_role` に実行権限がある。
- ただし `supabase/config.toml` の API 公開スキーマは `public` と `graphql_public` だけなので、**`private` の関数は supabase-js から呼べない**。
- 案：`public` に、この関数を呼ぶだけの関数を足し、実行権限は `service_role` だけに付ける（`anon` / `authenticated` からは呼べない）。ユーザーに数は返さない。
- 懸念：
  - なるほどの数は少ないうちは、誰が押したか推測できる可能性があるため、**ブラウザには返さず、サーバーの中で順番を決めるのにだけ使う**。
  - `private` スキーマを API に公開する方法もあるが、ほかの内部関数まで見えるようになるため避けたい。

### 2. 埋め込みベクトルの保存先

- 案：新しいテーブル `public.thread_embeddings` を作る。

  | 列 | 型 | 内容 |
  |---|---|---|
  | `thread_id` | uuid（主キー、`threads.id` を参照、削除時に一緒に消す） | どの意見のベクトルか |
  | `model` | text | 作ったモデル名（モデルを変えたら作り直すため） |
  | `embedding` | real[]（768個） | ベクトル |
  | `created_at` | timestamptz | 作った日時 |

- RLS を有効にし、**ポリシーは作らない**（`service_role` だけが読み書きする）。
- pgvector は使わない。1つの設問の意見は数十件程度なので、似ているかの計算はサーバーのプログラムで足りる。件数が大きく増えたら pgvector への切り替えを検討。
- 容量の目安：1件およそ3KB。1,000件で約3MB。
- 保存しない場合は、表示のたびに埋め込みAPIを呼ぶことになり、無料枠（非公式情報では1日1,000リクエスト程度）を使いやすくなるため、保存したい。
- 懸念：
  - 意見を削除・編集したときにベクトルが古くなる。削除は外部キーの `on delete cascade` で消える。**編集できる機能が今後できる場合は、作り直しの仕組みが要る**。
  - 意見の本文そのものではないが、本文から作った情報なので、意見と同じ扱い（非公開の意見のベクトルを外に出さない）にしたい。

### 3. サーバー用キー（`SUPABASE_SECRET_KEY`）を使う処理

- 上の1・2を読み書きするには、RLS を通らない `service_role` での接続が必要。
- `SUPABASE_SECRET_KEY` は `.env.local` にあるが、今のコードではまだ使っていない。
- 案：サーバー専用のファイル（Route Handler からだけ使う）で Supabase クライアントを作る。キーはブラウザに出さない。
- 懸念：
  - RLS を通らない接続なので、**このクライアントで書く処理は最小限にし、読み書きするテーブルを限定したい**。
  - Vercel など本番環境にも同じ環境変数を設定する必要がある。

## アプリ側の動き

- ベクトルは意見を投稿したときに、応答を返したあと（`after`）で1回だけ作って保存する。表示のときは Gemini を呼ばない
- 意見一覧 API は今までどおり新しい順。各意見に `representativeRank`（賛成・反対それぞれ 1〜3、代表でなければ `null`）を付ける
- なるほどの数はブラウザに返さない。キーやベクトルがないときは新しい順で選ぶ
- 本番環境には `SUPABASE_SECRET_KEY` と `GEMINI_API_KEY` の設定が必要
